# 검색 결과가 머리글 조각으로만 채워지는 문제

- 작성일: 2026-09-01
- 상태: 해결, 재인덱싱 필요
- 대상 문서: `doc_484fe06367a7` (키다리 아저씨, 545페이지 PDF)
- 관련 코드: `mineru_client.py`, `chunking.py`, `document_processor.py`, `config.py`

## 1. 요약

시멘틱 청킹으로 인덱싱한 545페이지 소설에 어떤 질문을 하든, 검색된 컨텍스트가
`키다리 아저씨\n\n(19세.` 같은 거의 동일한 조각들로만 채워져 LLM이 답하지 못했다.

임베딩 모델이나 검색 로직의 문제가 아니라 **인덱싱 단계에서 청크가 이미 망가져
있었다.** 원인은 서로 독립적인 세 가지였고, 셋 다 조용히(에러 없이) 동작했다.

수정 후 청크는 1081개 → 341개, 길이 중앙값은 158자 → 841자가 되었다.

## 2. 증상

사용자 질문 "키다리 아저씨는 어떤 사람인가"에 대해 `StuffDocumentsChain`에 주입된
컨텍스트:

```
키다리 아저씨

(19세.

키다리 아저씨

(19세.

키다리 아저씨

(19세.

키다리 아저씨

(22세.
```

LLM 응답: "제공된 문서에서 키다리 아저씨가 어떤 사람인지에 대한 정보는 찾을 수
없습니다."

후속 질문에서도 동일한 형태가 반복되었다. 검색은 정상 동작했고(k개를 반환했고),
프롬프트도 의도대로 조립되었다 — **문제는 검색된 청크의 내용 자체였다.**

## 3. 조사

증상만 보고 프롬프트나 리트리버를 손대는 대신, 실제로 Chroma에 무엇이 저장되어
있는지부터 측정했다.

### 3.1 저장된 청크 통계

```python
import sqlite3, collections, statistics
c = sqlite3.connect('app/storage/chroma_db/chroma.sqlite3')
rows = c.execute(
    "select id, key, string_value, int_value from embedding_metadata "
    "where key in ('chroma:document','chunk_index','chunking_strategy','page_number')"
).fetchall()
```

결과:

| 항목 | 값 |
|---|---|
| 전체 청크 수 | 1081 |
| 청크 길이 최소 / 중앙값 / 평균 / 최대 | 1 / 158 / 197.7 / 913 |
| 50자 미만 청크 | 192개 |
| 청킹 전략 | `semantic` |

`chunk_size` 설정값은 1000인데 **중앙값이 158자였다.** 설정이 조용히 무시되고 있었다.

### 3.2 페이지 단위 분석

| 항목 | 값 |
|---|---|
| 페이지 수 | 545 |
| 페이지당 청크 수 (최소/중앙/최대) | 1 / 2 / 3 |

가장 짧은 청크 5개의 내용은 각각 `'1'`, `'13'`, `'14'`, `'55'`, `'70'` — **페이지
번호뿐인 청크**였다.

5페이지의 청크 전체 내용:

```
'당신\n\n키다리 아저씨\n\n5'
```

본문 파편 + 러닝 헤더 + 페이지 번호. 이 시점에 두 가지가 동시에 드러났다:
페이지 부속물이 본문에 섞여 있고, 페이지 자체가 매우 작다.

### 3.3 머리글 오염 정도

```
'키다리 아저씨'를 포함한 청크: 621 / 1081 (57%)
```

대부분 청크의 **맨 앞**에 있었다. 임베딩이 이 반복 문자열에 지배되면서, 질문이
본문이 아니라 머리글에 매칭된 것이다.

### 3.4 MinerU 블록 타입 확인

```
text: 6915,  page_number: 545,  header: 117,  equation: 6,  image: 1
```

MinerU가 `header`/`page_number` 타입을 이미 붙여주고 있었는데 파이프라인이 쓰지
않고 있었다. 그런데 텍스트가 정확히 `'키다리 아저씨'`인 블록을 세어 보니:

```
type='text'   : 430개
type='header' : 116개
```

**러닝 헤더 546개 중 430개를 MinerU가 평범한 `text`로 분류**하고 있었다. 타입
필터만으로는 대부분을 놓친다는 뜻이다.

### 3.5 코드 경로 확인

- `mineru_client.py`의 `build_pages()`가 블록 타입을 구분하지 않고 모든 텍스트를
  `parts`에 넣고 있었다.
- `chunking.py`의 `SemanticChunker.split_documents()`가 Document를 하나씩 순회하고,
  `document_processor.load_pdf()`는 페이지당 Document를 하나씩 만든다.
- LangChain `langchain_text_splitters/base.py`의 `create_documents()`도 동일하다:

  ```python
  for i, text in enumerate(texts):
      for chunk in self.split_text(text):   # 각 text 안에서만 분할
  ```

  즉 **splitter는 Document를 쪼개기만 하고 절대 합치지 않는다.** `default`
  전략(`RecursiveCharacterTextSplitter`)도 마찬가지라, 전략을 바꿔도 해결되지
  않는다.

## 4. 근본 원인

### 원인 1 — 페이지 부속물이 본문에 섞임

`build_pages()`가 `header`/`page_number` 블록을 걸러내지 않아 러닝 헤더와 페이지
번호가 청크 본문에 그대로 들어갔다. 청크의 57%가 같은 문자열로 시작하면서 임베딩의
변별력이 사라졌다.

MinerU 타입만 믿을 수도 없었다 — 러닝 헤더의 79%(430/546)가 `text`로 분류되어
있었다.

**이것이 사용자가 본 증상의 직접적 원인이다.**

### 원인 2 — 청크가 한 페이지 안에 갇힘

splitter는 Document 경계를 넘지 못하고, Document는 페이지당 하나다. 따라서

> 청크 크기의 상한 = 페이지 크기

이 PDF는 큰 활자 레이아웃이라 페이지당 200자 남짓이어서 `chunk_size=1000`에
**도달 자체가 불가능**했다.

주의할 점은 이것이 어느 한 컴포넌트의 버그가 아니라는 것이다. 페이지 단위 Document는
출처 인용(페이지 번호, `image_ids`)을 위해 필요하고, splitter가 Document를 합치지
않는 것도 합리적이다 — 42쪽과 43쪽을 합친 청크의 `page` 메타데이터를 무엇으로
할지 splitter는 알 수 없다. 문제는 둘 사이의 **암묵적 가정**이었다:

> "페이지 하나는 `chunk_size`보다 크다"

일반적인 PDF 페이지(2000~3000자)에서는 성립하므로 아무도 명시하지 않았고, 검증하는
코드도 경고도 없었다.

### 원인 3 — 백분위 임계값을 Document마다 따로 계산

`SemanticChunker`가 경계 임계값을 각 Document 안에서 계산했다. 백분위는 상대
지표이므로, 내용과 무관하게 모든 Document에 비슷한 비율의 경계가 강제로 생긴다.
문장 두세 개짜리 페이지에서 95백분위를 구하는 것은 통계적으로 무의미하며, 주제
전환이 전혀 없는 페이지도 잘렸다(페이지당 청크 중앙값 2개).

## 5. 해결

### 5.1 페이지 부속물 제거 — `mineru_client.py`

두 겹으로 걸러낸다.

```python
_FURNITURE_BLOCK_TYPES = {"header", "footer", "page_number", "page_footnote"}
```

타입 필터로 잡히지 않는 나머지는 **행동 기반**으로 탐지한다:

```python
_RUNNING_TEXT_MAX_CHARS = 80         # 짧고
_RUNNING_TEXT_MIN_PAGES = 5          # 최소 5페이지에 등장하며
_RUNNING_TEXT_MIN_PAGE_RATIO = 0.2   # 전체 페이지의 20% 이상
```

`_running_furniture_texts()`가 이 세 조건을 **모두** 만족하는 문자열을 찾아
제외한다. 조건을 모두 요구하는 것이 과잉 제거를 막는 핵심이다 — 우연히 두 번
반복되는 짧은 구절이나, 반복되는 긴 문단은 살아남는다.

### 5.2 페이지 병합 — `chunking.py`의 `merge_pages()`

분할 **직전**에 같은 파일의 연속 페이지를 목표 크기까지 합치는 계층을 넣었다.
`document_processor.chunk_documents()`가 `splitter.split_documents()` 앞에서 호출하므로
`default`/`semantic` 두 전략 모두에 적용된다.

splitter가 스스로 판단할 수 없었던 메타데이터 결정은 `_merge_group()`이 명시적으로
내린다:

- 첫 페이지의 메타데이터를 유지 (인용이 청크 시작 지점을 가리키도록)
- 끝 페이지를 `page_number_end`로 기록
- `image_ids`는 순서를 보존한 **중복 제거 합집합** — 빠뜨리면 병합된 청크가
  인용하는 도표를 잃는다
- `ocr_used`/`full_page_ocr`는 OR, `ocr_image_count`는 합계
- `source`가 다르면 무조건 끊어 서로 다른 파일이 섞이지 않게 함

### 5.3 전역 임계값과 최소 청크 길이 — `SemanticChunker`

`split_documents()`가 모든 Document의 거리를 모아 임계값을 **한 번만** 계산한다.
청크 자체는 여전히 Document를 넘지 않고, 임계값만 공유한다.

`min_chunk_chars`를 추가해, 너무 짧은 청크를 만드는 경계는 건너뛰고 다음 청크로
넘긴다. 마지막에 남은 짧은 꼬리는 직전 청크에 붙인다.

클래스 기본값은 `0`으로 두어 노트북 포팅 동작 자체는 보존하고, 정책값은
`build_splitter()`가 설정에서 주입한다.

### 5.4 새 설정 (`config.py`)

```python
semantic_chunker_min_chunk_chars: int = 200
```

`chunk_size`는 이제 페이지 병합의 목표 크기도 겸한다.

부속물 제거의 정확도:

- 행동 기반 탐지로 걸린 문자열은 **`{'키다리 아저씨'}` 단 하나** — 과잉 제거 없음

남은 38%는 보일러플레이트가 아니라 본문 속 실제 언급이다. 예:

> 용돈은 매달 한 번씩 그 신사 분(키다리 아저씨)의 개인 비서를 통해 네게 보내어질 게다.

## 8. 남은 작업과 한계

- **재인덱싱 필요.** 수정은 인덱싱 단계에 있으므로, 기존 문서를 삭제하고 다시
  업로드해야 반영된다. (임베딩 341개 재생성)
- **`semantic` 경로는 실측되지 않았다.** 6절 수치는 임베딩 모델 로딩을 피하려고
  `default` splitter로 측정했다. `semantic` 경로는 단위 테스트로만 검증된 상태다.
- **문장 분리기의 한계는 그대로다.** `(?<=[.?!])\s+` 정규식에 의존하므로, 마침표
  없이 줄바꿈으로만 구성된 문서에서는 시멘틱 청킹이 여전히 의미 있게 동작하지
  않는다.
- **부속물 탐지 임계값은 경험값이다.** 이 문서 하나로 조정했다. 페이지가 매우 적은
  문서(5페이지 미만)에서는 `_RUNNING_TEXT_MIN_PAGES` 조건 때문에 러닝 헤더가
  탐지되지 않는다 — 의도적인 보수적 선택이다.

## 9. 배운 점

**증상이 나타난 곳과 원인이 있는 곳이 달랐다.** 증상은 검색/프롬프트 단계에서
보였지만 원인은 전부 인덱싱 단계에 있었다. 프롬프트나 `retrieval_k`를 조정했다면
아무것도 나아지지 않았을 것이다.

**세 원인 모두 에러 없이 조용히 실패했다.** `chunk_size=1000` 설정은 무시되고
있었지만 경고 한 줄 없었다. 저장된 데이터를 직접 측정하기 전까지는 드러나지
않았다.

이 문제는 이 프로젝트에 국한되지 않는다. LangChain으로 PDF RAG를 만드는 거의 모든
파이프라인에 원인 2가 잠재해 있으며, 페이지가 작은 문서(발표자료, 큰 활자, 스캔
문서)를 만나기 전까지 드러나지 않는다.
