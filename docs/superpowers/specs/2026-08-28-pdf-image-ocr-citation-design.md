# PDF 도표 이미지 출처 인라인 표시

- 작성일: 2026-08-28
- 개정: 2026-08-28 (현재 구현 기준 전면 재작성)
- 상태: 설계 승인됨, 구현 계획 대기

## 0. 개정 사유

이 문서의 최초 버전은 **텍스트 레이어만 인덱싱되고 PDF 임베디드 이미지의 내용이 통째로
유실되는 문제**를 다뤘다. 그 사이 `backend/app/services/ocr_service.py`,
`ocr_worker.py`, `pdf_ocr.py`가 별도로 구현되어 **이미 이 문제를 해결했다** — 단,
최초 버전이 전제한 것과는 다른 아키텍처로.

| | 최초 버전 (폐기) | 실제 구현 (현재) |
|---|---|---|
| OCR 엔진 | EasyOCR | **PaddleOCR**, 서브프로세스 격리 실행 (`SubprocessOCRService`) |
| 처리 단위 | 임베디드 이미지 1장 = 별도 인덱스 청크 | 이미지 영역을 OCR 텍스트로 **페이지 본문에 직접 치환**(splice-in) |
| 스캔본 전체 페이지 | 비대상(YAGNI)으로 명시 | **이미 구현됨** (`full_page_ocr`, 이미지가 많거나 텍스트가 거의 없는 페이지는 전체를 한 번에 OCR) |
| 신규 모듈 | `image_text_extractor.py` (미생성) | `pdf_ocr.py` + `ocr_service.py` + `ocr_worker.py` (이미 존재, 테스트 완비) |

즉 "OCR로 도표 텍스트를 인덱싱한다"는 목표 자체는 **이미 달성되어 있다.** 이 문서가 다루는
잔여 문제는 하나뿐이다: **검색된 청크가 이미지에서 유래했을 때, 사용자가 원본 도표를 눈으로
확인할 방법이 없다.** 최초 버전이 측정한 EasyOCR 신뢰도 실측치(0.8 임계값 등)는 다른 엔진
기준이라 이 개정판에는 이어받지 않는다 — PaddleOCR 쪽 튜닝은 이미 `ocr_min_score`,
`ocr_min_image_size` 등으로 별도 구현·테스트되어 있고 이 설계의 범위 밖이다.

## 1. 문제

`pdf_ocr.py`의 `extract_pages()`는 이미지 영역을 렌더링해 PaddleOCR에 넘기고, 인식된
텍스트를 페이지 본문 안에 `[이미지 텍스트]` 접두사와 함께 끼워 넣는다(`_format_ocr_block`).
이 텍스트는 청크로 쪼개져 인덱싱되고 검색된다 — 여기까지는 잘 동작한다.

문제는 그 다음이다. 검색된 청크가 도표에서 나온 것이라도, 사용자에게는 OCR이 인식한
**텍스트만** 보인다. OCR은 화살표·계층 구조·범례·표의 시각적 배치를 텍스트로 옮기지
못하고, 고유명사를 오인식하기도 한다(`야탑역` → `야람역` 등, PaddleOCR도 예외가 아니다).
사용자가 원본 이미지를 직접 볼 수 있다면 이 두 문제 모두 우회된다.

## 2. 설계 원칙 (유지)

OCR의 역할은 **사실 추출이 아니라 도표 발견**이다. 검색된 청크가 이미지에서 나온 것이면
**원본 이미지를 출처 카드 안에 인라인으로 보여준다.** 사용자는 자기 눈으로 도표를 읽으므로
OCR 오타가 정확성 문제에서 빠진다.

따름정리:

- 이미지-청크 연결의 정밀도는 중요하지 않다. 페이지 단위 근사로 충분하다 (3.1절).
- LLM은 OCR 텍스트의 고유명사를 단정해서는 안 된다. 프롬프트로 통제한다 (3.5절).

## 3. 설계

### 3.1 이미지-청크 연결: 페이지 단위 근사

현재 아키텍처는 페이지 하나를 하나의 `Document`로 만들고(`document_processor.load_pdf`),
그 뒤 `RecursiveCharacterTextSplitter`가 문자 수 기준으로 쪼갠다. 이미지가 본문 어디에
끼워졌는지는 청크 경계와 무관하게 잘릴 수 있어, **어느 청크가 정확히 어느 이미지에서
왔는지는 문자 오프셋만으로 정밀 추적할 수 없다.**

정밀 추적 대신 **페이지 단위로 근사한다**: 한 페이지에서 OCR로 성공적으로 텍스트를
얻은 이미지들의 ID를 그 페이지의 `Document.metadata["image_ids"]`에 리스트로 담는다.
`text_splitter.split_documents()`는 부모 메타데이터를 각 청크에 그대로 승계하므로,
**그 페이지에서 나온 모든 청크가 그 페이지의 이미지 전부를 인용**하게 된다.

이는 완벽하지 않다 — 텍스트만 있고 이미지와 무관한 청크도 같은 페이지에 이미지가
있으면 도표를 함께 보여주게 된다. 그러나 2절의 원칙대로 정밀도보다 발견 가능성이
중요하고, 사용자는 관련 없는 이미지면 무시하면 그만이다. 완벽한 청크-이미지 매핑을
만들려면 텍스트 분할기를 직접 다뤄야 하는데 그 복잡도는 이 문제의 가치에 비해 크다
(YAGNI, 4절).

### 3.2 이미지 저장

`pdf_ocr.py`가 이미지를 렌더링해 OCR에 넘기는 바로 그 지점에서 PNG로도 저장한다.
새 모듈을 만들지 않고 **`pdf_ocr.py` 자체를 확장**한다 — 이미 그 지점에 렌더링된
배열과 원본 바이트가 있고, `_ocr_image_block`은 이미 콘텐츠 md5를 캐시 키로 계산하고
있으므로 그 값을 이미지 ID로 재사용한다.

```
app/storage/images/{document_id}/{image_id}.png
```

- **블록 단위 이미지**: `image_id = md5(raw_image_bytes).hexdigest()[:16]`.
  같은 로고/헤더 이미지가 여러 페이지에 반복돼도 파일은 한 번만 쓰인다(같은 해시 →
  같은 파일 경로, 덮어쓰기는 멱등).
- **전체 페이지 스캔**: 블록 단위 원본 바이트가 없으므로(페이지 전체를 렌더링한
  픽스맵), `image_id = f"p{page_number}_full"`. 렌더링 DPI(`ocr_dpi`, 기본 200)를
  그대로 쓴다 — 화면 인라인 표시치고는 충분한 해상도이고 OCR용 렌더와 저장용 렌더를
  분리하는 비용을 들일 이유가 없다.
- **저장 실패는 OCR 결과에 영향을 주지 않는다.** 이미지 블록 단위 try/except 안에서
  저장하고, 실패하면 로그만 남기고 텍스트 인식 결과는 그대로 유지한다 (3.6절).

`document_id`는 현재 `process_file()`에 없으므로 인자로 추가한다. 호출부는
`upload.py` 한 곳이다. `document_id`가 없으면(예: 기존 테스트처럼 인자 없이 호출)
이미지는 저장하지 않고 텍스트 추출은 그대로 동작한다 — 하위 호환.

### 3.3 API

`SourceDocument`에 필드 하나를 추가한다. 리스트인 이유는 3.1절 때문이다 — 한 청크가
그 페이지의 이미지 여러 장을 인용할 수 있다.

```python
image_urls: list[str] = Field(default_factory=list, description="이 청크가 속한 페이지에서 발견된 도표 이미지 URL 목록")
```

`image_urls`는 `/api/v1/documents/{document_id}/images/{image_id}` 형태의
**상대 경로**다. 프런트엔드가 상대 경로로 API를 호출하도록 이미 구성돼 있으므로 Vite
프록시를 그대로 탄다.

신규 엔드포인트:

```python
@router.get("/{document_id}/images/{image_id}")
async def get_document_image(document_id: str, image_id: str) -> FileResponse
```

**보안**: `document_id`와 `image_id`는 사용자 입력이 파일 경로가 되는 지점이다.
정규식 화이트리스트(`^[A-Za-z0-9_]+$`)로 검증하고, 해석된 절대 경로가 이미지 저장소
루트 하위인지 `Path.resolve()` 후 재확인한다. 위반 시 404. 경로 안전 검사와 저장은
`app/services/pdf_ocr.py`가 아니라 `app/api/routes/documents.py`가 갖는다 — 저장
서비스에 FastAPI 의존성을 넣지 않기 위함이다(현재 `ocr_service.py`/`pdf_ocr.py`는
FastAPI를 전혀 import하지 않는다는 관례를 유지한다).

### 3.4 문서 삭제 시 이미지 정리

`documents.py`의 `delete_document`가 `vector_service.delete_by_document_id` 다음에
`app/storage/images/{document_id}` 디렉터리를 통째로 제거한다. 경로 검증은 3.3절과
동일한 화이트리스트를 재사용한다.

### 3.5 프롬프트

OCR 텍스트에는 `[이미지 텍스트]`(`settings.ocr_block_prefix`)가 **이미 본문에 인라인으로
박혀서 임베딩·검색·LLM 컨텍스트에 그대로 들어간다.** 즉 라벨링 인프라는 이미 있다 —
빠진 것은 LLM에게 그 마커의 의미를 알려주는 프롬프트 지침뿐이다.

최초 버전이 설계했던 "리트리버 래퍼로 청크 메타데이터에 라벨을 채우는" 접근은 필요
없다. 현재 구조에서 이미지 유래 텍스트는 청크 안에서 본문과 뒤섞여 있어(하나의 청크가
본문과 도표 텍스트를 함께 담을 수 있음) 청크 단위 라벨은 애초에 부정확하고, 텍스트
안의 마커가 이미 더 정밀하다.

`RAGService._initialize_llm`이 쓰는 `ConversationalRetrievalChain.from_llm`은 현재
커스텀 QA 프롬프트를 넘기지 않아 langchain 기본 프롬프트를 쓴다. 지침을 추가한
프롬프트를 `combine_docs_chain_kwargs={"prompt": QA_PROMPT}`로 넘긴다.

```python
QA_PROMPT_TEMPLATE = """다음 문맥을 참고해 질문에 답하라.
문맥 중 '[이미지 텍스트]'로 표시된 부분은 문서의 도표·이미지에서 문자 인식(OCR)으로
추출한 것이라 오탈자가 있을 수 있다. 이를 근거로 답할 때는 인명·지명 등 고유명사를
단정하지 말고, 해당 페이지의 도표를 직접 확인하도록 안내하라.

문맥:
{context}

질문: {question}
답변:"""
```

### 3.6 오류 처리

- 이미지 저장 실패는 **OCR 텍스트 추출을 실패시키지 않는다.** 블록 단위 try/except
  안에서 저장하고, 실패하면 로그만 남기고 계속한다. 텍스트 인식은 이미 별도로
  성공했을 수 있으므로 저장 실패 때문에 그 결과까지 버릴 이유가 없다.
- 이미지 저장 디렉터리 생성은 `mkdir(parents=True, exist_ok=True)`로 처리하고
  실패 시(디스크 문제 등) 해당 이미지만 건너뛴다 — 파일 업로드 자체를 실패시키지
  않는다. 이는 `load_pdf()`가 이미 채택한 "부분 성공이 전체 실패보다 낫다" 철학과
  일치한다(단, `load_pdf()`의 fallback은 파일 전체 단위이고 여기서 다루는 것은
  이미지 한 장 단위임에 유의 — 이미지 저장 실패가 상위 `try/except`로 전파돼
  텍스트 추출 전체가 PyPDFLoader 폴백으로 떨어지는 일이 없도록 반드시 이미지
  블록 내부에서 예외를 삼켜야 한다).
- 이미지 서빙 엔드포인트에서 경로 검증 실패나 파일 없음은 모두 404로 통일한다
  (실패 원인을 노출하지 않는다).

## 4. 범위

### 대상
- `pdf_ocr.py`가 이미 처리하는 모든 이미지 영역(블록 단위 + 전체 페이지 스캔)의
  원본을 저장하고, 그 페이지에서 나온 청크의 출처에 이미지 URL을 붙인다.

### 비대상 (YAGNI)
- 청크-이미지 정밀 매핑(문자 오프셋 기반) — 3.1절, 페이지 단위 근사로 충분
- VLM 기반 이미지 설명 생성 — 최초 버전에서 환각이 관측되어 기각된 결정을 유지
- 백그라운드 작업 큐 및 진행률 폴링 — OCR 파이프라인은 이미 업로드 요청 안에서
  동기 실행되고 있고, 이 기능(이미지 저장 1회 I/O 추가)은 그 타이밍 특성을 바꾸지
  않는다
- docx/txt의 이미지 처리 — 대상은 PDF뿐이다(현재 OCR 파이프라인 자체도 PDF 전용)
- OCR 신뢰도/필터링 튜닝 — `ocr_min_score`, `ocr_min_image_size` 등으로 이미
  별도 구현·테스트돼 있고 이 설계가 손댈 지점이 아니다

## 5. 설정

`Settings`에 하나만 추가한다. 나머지 OCR 튜닝 값은 이미 존재하므로 중복 정의하지
않는다.

| 키 | 기본값 | 근거 |
|---|---|---|
| `image_storage_dir` | `"app/storage/images"` | 업로드 원본(`upload_dir`), 벡터 DB(`chroma_persist_dir`)와 나란한 `app/storage/` 하위 규약을 따른다 |

## 6. 한계

- 청크-이미지 연결이 페이지 단위 근사라, 관련 없는 이미지가 함께 표시될 수 있다
  (3.1절). 사용자가 무시하면 되는 수준으로 판단해 수용한다.
- OCR이 심하게 깨진 도표는 애초에 검색되지 않아 이미지도 뜨지 않는다. 이 설계로
  해결되지 않는다.
- 전체 페이지 스캔 이미지는 `ocr_dpi`(기본 200) 해상도로 저장되며, 화면 인라인
  표시용으로는 충분하지만 확대해서 세부를 읽기에는 부족할 수 있다.
- `documents.py`의 문서 목록은 현재 빈 배열을 반환하는 미구현 상태다(`GET /`).
  이 설계는 거기에 의존하지 않지만, 문서 삭제 시 이미지 정리는 기존
  `delete_document` 경로에 얹는다.
